# Правила за агентите — KILN

## Контекст и обхват

Прочети конкретната Linear задача, [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md), [README.md](README.md) и [brief.md](brief.md). Прочети `DESIGN.md`, ако съществува. В K01 README, brief и този файл са резултат от задачата, не предварително условие. Не разчитай на историята на други чатове.

Работи само по възложената задача. Следвай ограниченията на проекта и етапите в плана. Изискванията на проекта, конкретният етап и използването на ImageGen имат предимство пред предложения на skills за друг workflow или финални изображения. Не разширявай обхвата с допълнителни страници, backend, база данни, акаунти или CMS.

## Комуникация и последователност

- Предварително описвай всяко планирано действие и причината за него с кратки булети на български.
- Вземи реалния Linear ID и преименувай текущия чат на `🔴 <ID>` при започване. При отворен PR той остава червен.
- Използвай отделни агенти, стартирани ръчно и последователно със Sol 6.1 / Medium според плана. Не стартирай следващ агент и не изпълнявай следваща задача.
- Преди K02–K15 потвърди, че PR на предходната задача е слят. K01 / SIN-32 е първа и няма предходна задача. Съответствията K01–K15 и реалните IDs са в плана.
- Обнови remote refs. Създай ново управлявано Codex worktree от последния `origin/main`, включващ слятата предходна задача, и нов клон `codex/<linear-id>-<кратко-описание>`; използвай ID с малки букви в клона.
- Редактирай само в своето worktree. Не променяй основния checkout или worktree на друга задача. Зависимостите, build файловете и preview сървърът са локални за worktree-то. При друг работещ preview използвай различен порт.
- В Linear: `In Progress` при старт, `In Review` след отваряне на PR, `Done` само след merge и изпълнени критерии. Използвай съответните налични статуси на екипа.
- Потребителят прави ревю и merge. Не сливай PR. Поискани поправки се правят от същия агент в същото worktree и PR.
- След потвърден merge и изпълнени критерии маркирай задачата Done и преименувай същия чат на `🟢 <ID>`.
- Запази worktree-то по време на ревюто. След merge и предаване на нужните файлове то може да се архивира чрез Codex. Не изтривай непредадени резултати.

## Четим TypeScript и React

- Включи TypeScript `strict` в K02 и го запази. Типизирай props, моделите на данните, състоянията на формата и границите между модулите. Оставяй TypeScript да извежда очевидните локални типове.
- Не използвай `any`, type assertions или изключване на проверки, за да прикриваш грешки. За неизвестни входни данни използвай `unknown` и проверка преди употреба.
- Използвай ясни английски имена, малки функции и компоненти с една разбираема отговорност. Разделяй представяне, данни и нетривиална логика, когато това улеснява четенето.
- Пиши идиоматични функционални React компоненти с hooks и композиция.
- Предпочитай прости условия и явен поток на данните пред вложени тернарни изрази, прекалено кратки записи и излишни абстракции.
- Добавяй коментари за нетривиална логика, ограничения или причината за решение. Пиши ги на прост английски, ниво B1, близо до съответния блок. Не преразказвай очевидния код.
- Проверявай четимостта преди всеки PR.

## Технически договор

- Next.js App Router, React, TypeScript strict и npm. K02 избира поддържана стабилна версия, съвместима с наличния Node; запази `package-lock.json`.
- `app/` съдържа страницата и layout-а, `components/` — секциите и интерактивните компоненти, `public/assets/` — финалните уеб изображения. Добавяй `lib/` и `scripts/` при реална нужда.
- Използвай CSS Modules и глобални CSS променливи. Phosphor само при смислена употреба. Прилагай приетия `DESIGN.md`, след като бъде създаден в K06.
- Настрой `output: 'export'` в `next.config.ts`. `npm run build` трябва да създава `out/` за GPT Sites. Менюто и демо формата са Client Components.
- Не използвай Server Actions, динамични сървърни маршрути или функции, изискващи работещ Next.js сървър.
- Оптимизирай изображенията предварително; използвай `<picture>`/`<img>`, responsive варианти и зададени размери. Не разчитай на сървърния оптимизатор на `next/image`.
- Не commit-вай `node_modules/`, `.next/`, `.next-dev/` или `out/`. Запази `skills-lock.json`, ако избраният инсталатор го създаде. Не commit-вай credentials.
- В K03 запиши точния commit, източника и начина за използване на Taste Skill. Финалните архитектурни изображения са от вградения ImageGen в K08; запази промптовете. Външните временни изображения имат записани източник и условия за използване.
- Всички видими текстове са на английски. CTA е “Discuss your project”. Демо формата проверява име, имейл и съобщение и при валидно попълване показва точно “Demo only — your enquiry has not been sent or saved.” Не изпраща и не съхранява данни и не внушава доставка на запитване. Подробностите са в brief.md.

## Проверки

- При документационни задачи провери пълнотата, съгласуваността и валидността на връзките. Не добавяй формални тестове без практическа нужда. Не отчитай бъдещи npm команди като изпълнени.
- При промени по кода изпълни TypeScript проверката, ESLint и production build с командите, настроени в K02. README трябва да съдържа точните команди след този етап.
- Проверки в браузър започват с първата цялостна версия; K05 е отделна контролна точка. След всяка визуална промяна проверявай засегнатите секции на компютър и телефон; основните ширини са 375, 768 и 1440 px.
- Проверявай преливане, четимост, навигация, зареждане на ресурси и грешки в конзолата. При взаимодействия проверявай клавиатурата, видимия фокус, предвидимото затваряне на менюто и reduced motion.
- Проверявай етикетите и грешките на формата с празни полета, невалиден имейл и валидно попълване. Потвърди липсата на мрежова заявка и запис на въведени данни.
- Преди деплой отвори самия `out/` през static server и провери менюто, формата и изображенията. Работещ `next dev` не е достатъчен.
- Провери контраст, заглавия, alt текстове, размери на изображенията, липса на видими скокове и отложено зареждане под първия екран. Следвай крайните критерии в плана.
- Ако проверка не може да се изпълни, опиши ограничението; не я отчитай като успешна.

## PR и публикуване

Отвори GitHub PR към `main` с реалния Linear ID в заглавието и връзка към issue в описанието. Опиши какво е променено, как е проверено и материалните ограничения. При визуални промени добави desktop/mobile снимки; при изисквано сравнение добави преди/след. Документационният K01 не изисква снимки на несъществуваща страница.

GitHub е основното място за код и ревю, GPT Sites — за публикуване. Sites синхронизацията не трябва да заменя GitHub remote, да заобикаля PR процеса или да добавя непроверени промени. При нужда подготви отделно копие на одобрения source за деплой.

K14 регистрира частен Site и добавя идентификатора и static конфигурацията за `out/` чрез PR, без публикуване. K15 публикува одобрения код от `main` и записва URL, GitHub commit и върнатата версия/статус на деплоя с проверка на хоствания сайт. Последващият PR е само отчет за предаване. Ако е нужна промяна по сайта, тя първо минава през PR и merge, после се публикува новата одобрена версия.

Site остава частен по подразбиране; публичното споделяне е отделно решение на потребителя. GitHub хранилището остава частно.
